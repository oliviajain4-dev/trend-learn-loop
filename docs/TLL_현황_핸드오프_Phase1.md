## 0. 이 문서를 읽는 코워크에게

사용자는 지금 **"내가 진짜 원하는 게 뭔지"를 다시 생각하려** 한다. 그래서 이 문서의 목적은

## 1. TLL 한 줄 정체

> **빠르게 변하는 IT/AI 기술을, "믿어도 되는 만큼만" 숫자로 보여주는 도구.**

- 북극성: 추천 정확도가 아니라 **측정된 충실도(faithfulness)** 로 "신뢰할 수 있는 이해"를 빠르게 형성(orientation).
- 정신 3가지: ① 측정 없는 주장 금지(신뢰도를 숫자로) ② 링크·수치는 API 원본만(LLM 생성 금지) ③ 검증은 결정론(코드)으로(검증기가 환각하면 안 됨).
- 맥락: **채용 사전 과제**. 평가자는 결과 완성도보다 **"AI를 어떻게 부렸는가"**(프롬프트·의심·수정·AI가 틀린 순간과 그 교정)를 본다. → `WORKLOG.md`·`ERRORS.md`가 핵심 제출물.

## 2. 지금까지 구현된 것 (Phase 1, 7조각 모두 완료)

파이프라인 흐름:
```
주제 → ① Collector → ② Analyst → ③ Verifier → ④ Metrics → ⑤ Dashboard
                                     └ 평행: ⑥ Eval-Harness (③④가 진짜 거짓 잡는지 실측)
       ⑦ Pipeline = ①~④를 한 줄로 엮어 data/briefs/*.json 생성
```

| # | 조각 | 위치 | 하는 일 | 상태 |
|---|------|------|---------|------|
| — | **데이터 계약** | `src/tll/schema.py` | 브리핑 JSON 형식·검증(stdlib dataclass, 매직 없음). 모든 모듈이 공유 | ✅ |
| 1 | **Collector** | `src/tll/collector/` | HackerNews(Algolia 검색)·GeekNews(Atom RSS) 무키 수집. robots·rate limit·provenance·중복제거·소스 다양성 | ✅ 실데이터 |
| 2 | **shared/llm** | `src/tll/shared/` | Gemini/Claude 프로바이더 추상화 + config(.env 전용 키 로더) + 레지스트리 | ✅ Gemini 실동작 |
| 3 | **Analyst(집필)** | `src/tll/analyst/` | 수집물→문장별 [S#] 브리핑 초안. **sid는 코드가 결정론 부여**, LLM은 그 출처만 인용(URL·수치 생성 금지) | ✅ 실 LLM |
| 4 | **Verifier(검증)** | `src/tll/verifier/` | **L1 인용 앵커링(결정론, LLM=0)**: 유령 인용 검출·제거, 미확인 이동 | ✅ 결정론 |
| 5 | **Metrics** | `src/tll/metrics/compute.py` | 충실도 지표(인용 유효율·커버리지·신뢰출처 지지율). 위반0이면 status="verified" | ⚠️ 결정론 프록시 |
| 6 | **Eval-Harness** | `src/tll/metrics/harness.py` | 환각 3유형 주입 → Verifier 검출률·오탐 실측 | ✅ 실측 |
| 7 | **Dashboard** | `src/tll/dashboard/` | Streamlit(localhost:8501): 신뢰도 게이지·상태배지·출처표·미확인 + 해커뉴스 트렌드 피드 | ✅ 가동 |
| 8 | **Pipeline** | `src/tll/pipeline/run.py` | collect→write→verify→metrics→저장. CLI: `python -m tll.pipeline.run "<주제>"` | ✅ end-to-end |

### 데이터(브리핑) 현황 — `data/briefs/`
- `rag.json`, `mcp.json`, `vector-db.json` — **샘플**(status="sample", 손으로 만든 것, 지표는 형식 확인용)
- `langchain.json` — **파이프라인 실제 생성물**(status="verified", collect→집필→검증→측정 거침)

## 3. 실제로 "진짜"인 것 vs "프록시/유보"인 것 (정직한 현황)

이게 방향 재고의 핵심이라 명확히 구분한다.

### ✅ 진짜로 동작하는 것
- HackerNews·GeekNews **실데이터 수집**(점수·링크·날짜 원본, 지어냄 없음 — 원천 재호출로 대조 검증까지 함)
- Gemini로 **실제 브리핑 집필**([S#] 인용, 유령 인용 0)
- **L1 결정론 검증**: 유령 인용을 100% 잡음(같은 입력→같은 판정)
- **Eval-Harness 실측**: 브리핑 4·주입 12 → **검출률 1.0, 오탐 0**
- **파이프라인 end-to-end** + **대시보드** 렌더

### ⚠️ 프록시이거나 정직하게 유보한 것 (과장 안 함)
| 항목 | 지금 상태 | 왜 | 열려면 필요한 것 |
|------|-----------|-----|-----------------|
| **atomic-fact 지지율(FActScore)** | 결정론 프록시(신뢰출처 인용 비율) | 진짜는 문장 단위 원문 대조 필요 | 출처 **본문 전체** 수집 |
| **RAGAS faithfulness** | 커버리지 프록시 | 진짜는 NLI 필요 | 본문 + NLI |
| **L4 NLI 인용검사** | 미구현(유보) | 인용 passage가 문장을 함의하는지 = 본문 필요 | 본문 수집 |
| **CoVe(검증질문·독립답변)** | 미구현(유보) | 출처 본문 없이 돌리면 **검증기가 환각** → 철학 위반 | 본문 수집 |
| **L3 교차모델 검증(Claude)** | 미구현 | **.env의 ANTHROPIC_API_KEY가 실제 키가 아니라 한글 자리표시("여기에…")** | 진짜 Claude 키 |
| **다관점(STORM)·YouTube·Reflexion** | 미착수 | Phase 2·3 범위 | — |

> **핵심 통찰**: 지금 "검증"의 반쪽은 **본문 원문을 안 가져와서** 막혀 있다.
> Collector가 기사 **본문**까지 수집하면 L4/CoVe·진짜 지표가 "유보"에서 "실측"으로 승격된다.
> → **가장 값어치 큰 다음 한 걸음일 가능성이 높다.**

## 4. 기술 스택·실행법

- Python 3.10(.venv), 린트 ruff. 의존성: streamlit·plotly·requests·python-dotenv·google-genai·anthropic.
- 키: `.env`에 `GEMINI_API_KEY`(동작), `ANTHROPIC_API_KEY`(자리표시=미발급), `YOUTUBE_API_KEY`(있음, 미사용).
  - Gemini 기본 모델: `gemini-flash-lite-latest` (무료 티어에서 2.5-flash는 404, 이것만 그린패스 — 실측으로 확정).
- 실행:
  ```
  .\.venv\Scripts\Activate.ps1
  streamlit run src/tll/dashboard/app.py          # 대시보드 http://localhost:8501
  python -m tll.pipeline.run "RAG" hackernews     # 파이프라인으로 브리핑 생성
  ```

## 5. 검증/증거 (과제 제출물로 쓸 수 있는 것)

- **Eval-Harness 리포트**: 검출률 1.0·오탐 0, 그리고 **"못 잡는 유형(유효 인용+거짓 내용)"까지 정직하게 노출** ← "AI가 틀리는 순간과 그걸 잡는 법"의 실측 증거.
- **`WORKLOG.md`**: 막힘→뚫음 시간순 기록(예: RSS인 줄 알았는데 Atom이었다, HN이 "RAG"를 "Rage"로 오탐).
- **`ERRORS.md`**: AI가 틀린 순간 4건(미사용 import, 지원종료 API, Gemini 모델명 404 추측, 짧은 유령인용 지표 누락) + 각 수정.
- **커밋 이력**: 21커밋, 전부 `feat/ny:`/`docs/ny:` + 단계 라벨(`[N단계]`), 하위단계 1개=커밋 1개.

## 9. ★ 다시 생각해볼 지점 (사용자가 방향 재고할 열린 질문)

1. **"진짜 산출물"이 무엇인가?**
   - (a) 사람이 읽는 **브리핑/대시보드**가 핵심인가, (b) **검증 하네스 + 충실도 실측**이 핵심인가?
   - 기획서는 (b)("점수를 참이게 만드는 하네스")를 중심이라 했는데, 지금 눈에 보이는 건 (a)다. 어디에 무게를 둘지.

2. **본문 수집을 할 것인가?** — 지금 검증의 반쪽이 여기서 막혀 있다.
   - 하면: L4/CoVe·진짜 FActScore/RAGAS가 "유보→실측"으로 승격(가장 큰 값 상승).
   - 비용: robots·스크래핑·본문 파싱·토큰 증가. 소스별 난이도 다름.

3. **충실도 지표를 어디까지 "진짜"로?** — 결정론 프록시로 충분한가, NLI/LLM 채점까지 갈 것인가.
   - 과제 관점: "프록시임을 정직하게 밝힌 것"도 강점. 굳이 더 갈 필요가 있나?

4. **교차모델 검증(Claude)** — 실제로 켤 것인가? (실 키·비용 발생) 안 켜도 정직 고지로 충분한가?

5. **에이전트성** — 전환점 1(재수집 결정)을 얇게 넣어 "하이브리드 데모"를 만들 것인가? 아니면 워크플로우로 두고 그 경계를 라벨링하는 것 자체를 증거로 삼을 것인가?

6. **범위 vs 깊이** — Phase 2(다관점·YouTube)로 **넓힐지**, Phase 1 유보항목(본문·진짜 검증)으로 **깊게 팔지**.

7. **평가 기준** — 이 과제에서 "성공"을 무엇으로 볼 것인가? (충실도 실측치? 데모 완성도? **AI 활용 기록의 질**?) 이게 정해지면 위 1~6의 답이 거의 따라온다.

## 10. 코워크에게 던질 질문 후보

- "지금 상태에서, **채용 과제 관점으로** 가장 임팩트 큰 다음 한 걸음은 무엇인가? 넓히기(Phase 2) vs 깊게(본문 수집→진짜 검증) 중 어디에 무게를 둬야 하나?"
- "검증의 반쪽이 본문 미수집으로 막혀 있다. 본문 수집을 핵심으로 올리는 게 맞나, 아니면 '프록시임을 정직히 밝힌 현재'가 이미 충분한 증거인가?"
- "이 프로젝트의 진짜 산출물은 브리핑(대시보드)인가, 검증 하네스(충실도 실측)인가? 둘 중 무엇을 전면에 내세워야 평가자에게 잘 읽히나?"
- "지금까지의 WORKLOG/ERRORS(AI가 틀린 순간과 교정)가 과제의 핵심이라는데, 이걸 더 잘 드러내려면 뭘 해야 하나?"

## 11. 한 줄 요약

**Phase 1(수집→집필→L1검증→측정→대시보드)이 end-to-end로 동작하고 검출률 1.0으로 실측됐다. 다만 "검증의 깊이(본문 기반 L4/CoVe·진짜 지표)"는 본문 미수집으로 정직하게 유보 중. 이제 넓힐지(Phase 2) 깊게 팔지(본문 수집), 그리고 브리핑 vs 하네스 중 무엇을 전면에 둘지를 정할 시점이다.**
