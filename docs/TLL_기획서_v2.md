# TLL (Trend · Learn · Loop) — 기획서 v2 (마스터)

> 작성: 2026-07-10 · 상태: **설계안(구현 전, 승인 대기)** · v1을 대체
> 개정 근거: `TLL_평가_논문기반_v1.md` (STORM·ALCE·CoVe·FActScore·Reflexion·RAGAS·Deep Research survey 기준 채점, v1≈51 → v2≈83)
> 전략 원칙: **점수는 기능 추가로 올리지 않는다. 지금 주장(검증·충실도)을 "측정으로 참이게" 만들어 올린다. 그 도구가 평가 하네스다.**

---

## 0. 미션 재정의 (근본 프레이밍)

**"배울지 말지"는 목적이 아니라 부산물이다.** TLL의 북극성은:

> **빠르게 변하는 IT/AI 기술에 대해 "신뢰할 수 있는 이해"를 빠르게 형성해, 사용자가 불확실성을 줄이고 방향을 잡게 한다 (orientation).**

- 좋은 이해가 서면 배울지·쓸지·추적할지는 저절로 따라온다.
- 1차 성공 지표 = 추천 정확도가 아니라 **산출된 이해의 충실도(faithfulness), 측정된 값.**
- 근거: Deep Research 문헌은 이 일을 "판단"이 아니라 **knowledge synthesis**로 정의(arXiv:2508.12752). "뭐가 비슷/다른가"는 **대조·유추 설명**으로 TLL의 핵심 산출 방법으로 승격.

## 1. v1 → v2 변경 요약 (무엇을·왜)

| # | 변경 | 이유(논문) |
|---|------|-----------|
| ① | 미션을 "판단"→"검증된 이해 형성(orientation)"으로 | Deep Research=knowledge synthesis |
| ② | 충실도를 **숫자로 측정**(atomic-fact 지지율 + RAGAS faithfulness) | FActScore, RAGAS: 측정 없으면 개선·신뢰 주장 불가 |
| ③ | 검증기를 **CoVe 구조**(독립 검증질문)로 재설계 + 결정론 앵커링 유지 | Chain-of-Verification: 초안 편향 제거, F1 +23% |
| ④ | 인용을 **NLI 기반 품질 지표**로 | ALCE: citation precision/recall |
| ⑤ | 집필 전 **다관점 질문 생성** | STORM: 커버리지·균형 |
| ⑥ | Loop를 **Reflexion 구조**로(Actor/Evaluator/Self-Reflection+메모리) | Reflexion: 측정가능한 반복 개선 |
| ⑦ | **평가 하네스를 Phase 1에 포함** (핵심) | 검증기가 실제로 거짓을 잡는지 실측 |
| ⑧ | '비교' 섹션을 **대조·유추 설명 방법**으로 명문화 | 인지과학, STORM |

**핵심 전략(사용자 합의)**: C1(충실도 20점)·C2(검증 15점)·C3(인용 12점)은 "설계됨"에서 "입증됨"으로 올라가야 상단 점수가 열린다. 그 유일한 경로가 **하네스(C5)** 다. 따라서 하네스를 Phase 1의 중심에 둔다. C7(개념연결)은 폴리싱, C8·C9는 점수 위해 손대지 않는다(엄밀성과 상충).

## 2. 파이프라인 (Deep Research 4단계 + 검증·측정 강화)

```
① Planning
   └ 주제 확정 + 조사 계획
② Multi-perspective Question 생성 (STORM)
   └ 관점별 질문: [개발자] [출시 회사/저자] [회의론자] [실사용자] [비교대상]
③ 수집 (Collector) — 공식 API 우선, robots, rate limit, provenance 박제
④ 집필 (Analyst) — §3 양식, 모든 사실 문장에 [S#]
⑤ 검증 (Verifier) — CoVe + L1 결정론 앵커링 + NLI 인용검사
   초안 → 검증질문 생성 → 출처만 보고 독립 답변 → 불일치 문장 삭제/수정
⑥ 지표 산출 (Metrics) — atomic-fact 지지율 · RAGAS faithfulness · 인용 P/R
⑦ 산출 (Presenter) — '신뢰도'를 측정된 실수치로 표기
⑧ Loop (Reflexion) — 사용자·측정 피드백을 메모리에 → 다음 반복 개선
평행: 평가 하네스가 ⑤⑥을 골드셋으로 상시 검증
```

## 3. 산출물 — "정체 브리핑" 표준 양식 (교과서형, v2)

각 기술 1건당. 헤더에 **측정된 신뢰도** 노출.

```
# {기술명} — 정체 브리핑
충실도: atomic-fact 지지율 92% · 인용정밀도 0.88 · 출처 {n}개 · 최초확인 2026-07-08

0. 한 줄 정체 [S1]
1. 큰 뼈대(구조/틀) [S1][S2]
2. 왜 나왔나(배경·계보) [S2]
3. 대조·유추: 뭐가 비슷/다른가 — "X는 Y와 구조는 같으나 Z에서 다름", 내 KB 기존개념에 연결 [S2][S3]
4. 왜 필요한가/어떤 문제를 푸나 [S1][S4]
5. 전망(객관): 채택신호·한계·리스크 균형 [S3][S5]
6. 바로 따라하기(quickstart) [S1]
7. 미디어: 유튜브 글로벌10 + 한국어10 (YouTube API 실데이터)
8. 사람들의 반응(여론, 사실 아님) — HN/Reddit/댓글 감성 + 링크
9. 판단 도우미: 배울 가치·성숙도·나와의 관련성
── 출처(provenance) [S#] 제목·기관·발행일·등급·URL·수집시각
── ⚠️ 미확인·충돌: 근거 약한 주장, 출처 간 모순을 정직하게
```

## 4. 검증 스택 v2 (설계의 심장) — "LLM 판단보다 코드·API를 믿는다"

### 4-1. CoVe 기반 검증 절차 (P3)
1. **초안** — Analyst가 [S#] 달아 집필.
2. **검증질문 생성** — 각 사실 문장에서 검증질문 자동 생성("이 수치/주장/날짜가 맞는가?").
3. **독립 답변** — 초안을 *가리고* 출처 텍스트만 보고 질문에 답(초안 편향 차단 = CoVe 핵심).
4. **수정** — 독립 답변과 불일치하면 문장 삭제/수정.

### 4-2. 위에 겹치는 결정론·지표 층
| 층 | 이름 | 방식 | 기본 |
|---|------|------|:---:|
| L1 | 인용 앵커링(결정론) | 사실 문장의 인용문이 원문에 **문자열로 실제 존재**하는지 코드 검사. 없으면 폐기. LLM 판단 0 | ✅ |
| L2 | 다중출처 확인 | 독립 2+ 출처 일치 시 "확인". 단일은 태그 | ✅ |
| L3 | 교차모델 심판 | 초안=모델A, 검증=모델B(Gemini↔Claude) | ✅ |
| L4 | NLI 인용검사(ALCE) | 인용 passage가 문장을 **함의(entail)** 하는가 → 인용 정밀도/재현율 | ✅ |
| L5 | 자기일관성 | n회 반복, 매번 나오는 것만 채택 | 옵션 |
| L6 | 모순탐지 | 반대 출처도 찾아 충돌은 그대로 노출 | 옵션 |

### 4-3. 링크·수치는 API에서만
유튜브 링크·조회수, 깃허브 스타 등 URL·숫자는 **LLM이 생성 금지**. API/피드 원본→코드 삽입.

### 4-4. 정직 원칙
근거 약하면 채우지 말고 "미확인" + 신뢰도 하향. 신기술 특성상 자주 발생 = 오히려 신뢰의 근거.

## 5. 충실도 측정 (C1의 핵심, "신뢰도를 감이 아니라 숫자로")

- **Atomic-fact 지지율 (FActScore식, P4)**: 브리핑을 원자 사실로 분해 → 각 사실이 신뢰 출처(1·2급)에 의해 지지되는 비율. 예 92%.
- **RAGAS faithfulness (P6)**: 문장이 검색 문맥에 의해 뒷받침되는 정도(참조 없이).
- **인용 정밀도/재현율 (ALCE, P4-2)**: 인용이 실제로 지지하는가 / 불필요 인용 없는가.
- 이 세 수치를 브리핑 헤더에 노출. 임계 미달 섹션은 자동 "미확인" 처리.

---

## 6. ★ 평가 하네스 (C5) — Phase 1의 중심, 점수를 "진짜로" 올리는 도구

목적: **내가 설계한 검증기가 실제로 거짓을 잡는지 실측**한다. 이게 없으면 C1·C2·C3는 영원히 "설계됨"에 묶임.

구성:
1. **골드셋** — 이미 잘 아는 기술 5~10건(사실/출처 정답 보유).
2. **환각 주입 테스트** — 원문에 없는 문장/가짜 링크/틀린 수치를 일부러 삽입 → 검증기가 몇 % 잡아내는지 = **환각 검출률(recall)**, 오탐(false positive)도 측정.
3. **지표 리포트** — atomic-fact 정밀도, 인용 P/R, 환각 검출률, 통과율. 실행마다 기록.
4. **회귀 감시** — 프롬프트·모델 바꿔도 지표가 떨어지지 않는지.

산출물은 과제의 "AI가 틀리는 순간과 그걸 잡는 법" 증거로 그대로 사용.

## 7. 다관점 연구 (C4, STORM P1)
집필 전, 관점별 질문 세트를 생성해 수집·집필을 구동: [개발자=어떻게 쓰나] [출시사/저자=무엇을 주장하나] [회의론자=한계·비판] [실사용자=실제 반응] [비교대상=선행/경쟁 기술]. → 커버리지·균형 확보, 한쪽 홍보성 서술 방지.

---

## 8. Loop = Reflexion 구조 (C6, P5)
- **Actor** = Analyst(집필).
- **Evaluator** = Verifier + 지표(충실도·인용·환각 검출률).
- **Self-Reflection** = 실패를 언어로 기록해 에피소드 메모리(`lessons`)에 저장 → 다음 집필/검증이 그 출처·패턴 회피.
- **측정가능한 반복**: 같은 주제 재생성 시 지표가 오르는지 로깅.
- 개인화·부상감지 오버라이드(내가 넘겨도 뜨면 재소환)·감쇠는 v1 그대로 유지.

## 9. 모듈 지도 (v2)
```
[Planner] → [Q-Generator 다관점] → [Collector 수집·provenance]
      → [Analyst 집필·인용] → [Verifier CoVe+L1~L4] → [Metrics 충실도·인용]
      → [Presenter 산출·신뢰도수치] → [Memory/Loop Reflexion]
[Eval-Harness] ── 골드셋·환각주입으로 Verifier·Metrics 상시 검증
[shared] LLM추상화(Gemini/Claude) · config/.env · rate limiter · 로깅
```

## 11. 구현 계획 v2 (핵심 우선, 하네스 포함)
**Phase 1 — 뼈대 + 검증 + 측정 (제출 최소선)**
1. shared/llm(provider 추상화)
2. Collector(무키 소스: arXiv·HN·RSS) + provenance
3. Analyst(문장별 [S#])
4. Verifier = **CoVe + L1 앵커링 + L4 NLI 인용**
5. **Metrics + Eval-Harness**(골드셋 3~5 + 환각 주입 + 환각 검출률) ← 점수를 참이게 만드는 핵심
6. Presenter(한 페이지, 신뢰도 실수치)

**Phase 2** — 다관점 질문(STORM) 전면 적용, L2 다중출처, YouTube API(10+10)·반응
**Phase 3** — SQLite KB, Reflexion Loop(측정된 반복 개선), 부상감지
**Phase 4(로드맵)** — 임베딩 클러스터링, 스케줄·알림, L5/L6
